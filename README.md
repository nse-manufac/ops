# ops — แดชบอร์ดของทีม agent

หน้าเดียวที่ตอบว่า **ทีม agent ทำอะไรไปบ้าง มีอะไรรอเราอยู่ และใช้เงินไปเท่าไร**
ครอบคลุม `nse-manufac/store` และ `nse-manufac/plan`

👉 https://nse-manufac.github.io/ops/

---

## repo นี้ทำอะไร

ทุก 30 นาที มันจะ

1. ถาม GitHub ว่า agent ของทั้งสอง repo รันอะไรไปบ้าง
2. ดึงราคาและจำนวนเทิร์นของแต่ละรอบออกจาก log
3. เขียน `index.html` ใหม่แล้ว commit — GitHub Pages เผยแพร่ให้เอง

**ไม่มี agent อยู่ใน repo นี้** มีแต่สคริปต์ที่คนเขียน (`scripts/build.py`)

## ตั้งค่าครั้งเดียวตอนเริ่ม

### 1. สร้าง PAT แบบอ่านอย่างเดียว

github.com/settings/personal-access-tokens → **Generate new token**

| ช่อง | ค่า |
|---|---|
| ชื่อ | `ops-dashboard-read` |
| Repository access | Only select repositories → เลือก **store** และ **plan** |
| Repository permissions | **Actions: Read-only** · **Contents: Read-only** · **Issues: Read-only** · **Pull requests: Read-only** |

> **ห้ามให้สิทธิ์เขียนอะไรทั้งสิ้น** token นี้ทำหน้าที่อ่านอย่างเดียว
> การเขียน `index.html` ใช้ `GITHUB_TOKEN` ของ repo นี้เอง ซึ่งแตะ repo อื่นไม่ได้

### 2. ใส่เป็น secret

github.com/nse-manufac/ops/settings/secrets/actions → **New repository secret**

ชื่อ `READ_AGENTS_PAT` (ตรงตัวพิมพ์)

### 3. เปิด Pages

Settings → Pages → Source = **Deploy from a branch** → `main` / `(root)`

`GITHUB_TOKEN` ของ repo นี้อ่าน Actions API ของ repo อื่นไม่ได้ ถึงจะเป็น public ก็ตาม

ผลพลอยได้คือขอบเขตชัดมาก — token ที่เก็บไว้ที่นี่ **อ่านได้อย่างเดียวและอ่านได้แค่สอง repo นั้น**
ต่อให้หลุดออกไป ก็อ่านได้เฉพาะสิ่งที่เป็นสาธารณะอยู่แล้ว

## หลักที่ใช้ตัดสินว่าอะไรรวม อะไรแยก

**รวมได้เฉพาะสิ่งที่แชร์กันจริง** — บิลใบเดียวกัน กับคิวความสนใจของเจ้าของ

**ที่เหลือแยกรายทีมทั้งหมด** เพราะทุกอย่างที่ลงมือทำกับมันเป็นรายทีม —
เพดานปรับแยก · key เพิกถอนแยก · prompt แก้แยก

ตัวเลขรวมอย่าง "หัวหน้าทีมใช้ไป $2.00" เอาไปตัดสินใจอะไรไม่ได้
แต่ "หัวหน้าทีมของ plan แพงกว่าของ store 28%" เอาไปทำอะไรต่อได้

## เรื่องที่ควรรู้

**ราคาอยู่ใน log ดิบเท่านั้น** ไม่มี API ให้ถามตรง ๆ ต้องโหลด log ทั้งไฟล์มาหา
ซึ่งกินเวลา 3–5 วินาทีต่อรอบ จึงเก็บ `data.json` ไว้เป็น cache และอ่านเฉพาะรอบใหม่

**GitHub เก็บ log ไว้ 90 วัน** รอบที่เก่ากว่านั้นอ่านราคาไม่ได้อีก
แต่เพราะ cache ไว้แล้ว ตัวเลขเก่าจึงไม่หายไปจากแดชบอร์ด — **อย่าลบ `data.json`**

**รอบที่ถูกข้ามไม่ปรากฏในตาราง** เพราะไม่ได้เรียกโมเดลและไม่มีค่าใช้จ่าย
ส่วนรอบที่ล้มแล้วเสียเงินจะขึ้นเป็นแถวจาง ๆ พร้อมนับรวมใน "เสียเปล่า"

**เพดานเป็นของใครของมัน** `store` 6 + `plan` 6 = ช่างซ่อมรันได้ 12 รอบ/วัน ไม่ใช่ 6
ปรับที่ Settings → Variables → `AGENT_MAX_RUNS_PER_DAY` ของแต่ละ repo

## รับเรื่องจากพนักงานทาง LINE (`line/Code.gs`)

พนักงานพิมพ์อาการเข้ามาในแชท → เลือกว่าเป็นโปรแกรมไหน → ระบบเปิด issue ให้
หัวหน้าทีมอ่านโค้ดตรวจสอบ แล้ว**ส่งคำตอบกลับมาที่แชทเดิม**ภายในไม่กี่นาที

### เส้นแบ่งที่สำคัญที่สุด

| ใครสั่งได้ | ทำอะไรได้ |
|---|---|
| พนักงานผ่าน LINE | ปลุกหัวหน้าทีมให้วิเคราะห์ — **อ่านอย่างเดียว** |
| เจ้าของเท่านั้น | อนุมัติให้ช่างซ่อมลงมือแก้โค้ด |

bot สร้าง issue ด้วย PAT ของเจ้าของ ทุกเรื่องจาก LINE จึงดูเหมือน "เจ้าของเป็นคนเปิด"
ด่าน `author == owner` เดิมจึงผ่านฟรี — ถ้าไม่ทำอะไรเพิ่ม เท่ากับใครก็ตามที่เป็นเพื่อนกับ OA
สั่งให้แก้โค้ด production ได้

`agent-implement.yml` ของทั้งสอง repo จึงมีด่านเพิ่ม: ถ้า issue มีป้าย `จาก-LINE`
จะอ่าน timeline ดูว่า **ใครเป็นคนติดป้าย `ready-to-fix`** ถ้าไม่ใช่เจ้าของ จะไม่ส่งต่อ
ตรวจด้วยเครื่อง ไม่ใช่คำสั่งใน prompt — ต่อให้หลอกหัวหน้าทีมสำเร็จก็ไม่ผ่าน

### ตั้งค่า

**1. LINE Developers Console** — สร้าง Messaging API channel เอา **Channel access token** มา
ปิด auto-reply กับ greeting message ทิ้ง ไม่งั้นจะตอบซ้อนกับ bot

**2. Apps Script** — สร้างโปรเจกต์ใหม่ วาง `line/Code.gs` ลงไป
แล้วใส่ Project Settings → Script properties

| ชื่อ | ค่า |
|---|---|
| `LINE_TOKEN` | Channel access token |
| `HOOK_KEY` | สุ่มเอง 32 ตัวอักษร — ใช้เป็นกุญแจต่อท้าย URL |
| `GH_TOKEN` | PAT สิทธิ์ **Issues: Read and write** บน store กับ plan |
| `INTAKE_TOKEN` | PAT สิทธิ์ **Contents: Read and write** บน `intake` ตัวเดียว — ไม่ใส่ก็ได้ จะกลายเป็นรับเฉพาะข้อความ |
| `ALLOW` | เว้นว่างไว้ก่อน เดี๋ยวค่อยเติมทีหลัง |

**3. Deploy ครั้งแรก** → New deployment → Web app → Execute as **Me** · Who has access **Anyone**
เอา URL มาต่อท้าย `?k=<HOOK_KEY>` แล้วใส่เป็น Webhook URL ใน LINE console

> ⚠️ **ตอนอัปเดตโค้ดทีหลัง ห้ามกด New deployment**
>
> ถูกคือ **Manage deployments → กดดินสอแก้ตัวที่ใช้อยู่ → Version: `New version` → Deploy**
> URL จะคงเดิม ไม่ต้องแตะ LINE webhook และไม่ต้องแตะ `LINE_HOOK_URL` ทั้งสอง repo
>
> ถ้าสร้าง deployment ใหม่ จะได้ URL ใหม่ แล้วต้องตามไปแก้ **3 ที่** (webhook + secret สอง repo)
> ตัวเก่ายังทำงานอยู่ด้วย ถ้าลืมแก้ secret คำตอบจะยังวิ่งเข้าโค้ดเวอร์ชันเก่า
> ซึ่ง relay ได้ปกติ เลยดูเหมือนทุกอย่างเรียบร้อยทั้งที่ครึ่งระบบเป็นของเก่า
>
> และ **กด Ctrl+S เฉย ๆ ไม่พอ** — `/exec` เสิร์ฟเวอร์ชันเดิมจนกว่าจะสร้าง version ใหม่
> (`/dev` เสิร์ฟโค้ดล่าสุดเสมอ แต่ต้องล็อกอิน ใช้เป็น webhook ของ LINE ไม่ได้)

**4. เปิดสิทธิ์ให้พนักงาน** — ให้เขาทักมาหนึ่งครั้ง bot จะตอบรหัสกลับไป
เอารหัสนั้นมารัน `เพิ่มผู้ใช้('U...')` ในหน้า Apps Script

**5. ให้ส่งคำตอบกลับได้** — ใส่ secret `LINE_HOOK_URL` (URL เต็มพร้อม `?k=`)
ในทั้ง `store` และ `plan` ถ้าไม่ใส่ ระบบยังทำงานปกติ แค่ไม่ส่งกลับ LINE

### ใช้ในกลุ่ม

ลากบัญชีเข้ากลุ่มได้เลย พอเข้าไปแล้วมันจะ**แนะนำตัวและสอนวิธีใช้เอง** พร้อมบอกรหัสกลุ่มไว้ให้เปิดสิทธิ์

พนักงานเรียกด้วยการพิมพ์

```
#แจ้ง กดปุ่มบันทึกแล้วยอดไม่ขึ้น
```

**ข้อความอื่นในกลุ่มจะถูกข้ามทั้งหมด** ไม่ตอบ ไม่เก็บ ไม่เปิดเรื่อง

> ⚠️ ข้อนี้สำคัญกว่าที่ดู — LINE ส่ง **ทุกข้อความ** ในกลุ่มมาให้ bot เหมือนแชทเดี่ยวเป๊ะ ๆ
> ([เอกสาร LINE](https://developers.line.biz/en/docs/messaging-api/group-chats/))
> ถ้าไม่กรองด้วยคำสั่งเรียก มันจะพยายามเปิดเรื่องจากทุกบทสนทนา

**ต้องเปิดใน OA Manager ก่อน** — การตั้งค่า → อนุญาตให้เพิ่มบัญชีเข้ากลุ่ม

**เปิดสิทธิ์รายกลุ่ม** เอารหัสที่ bot บอก (`C...`) ไปต่อท้าย `ALLOW` ครั้งเดียว ทุกคนในกลุ่มนั้นแจ้งได้เลย ไม่ต้องเพิ่มทีละคน

**คำตอบจะกลับเข้ากลุ่ม** ไม่ใช่ทักคนแจ้งส่วนตัว — ตั้งใจให้เป็นแบบนั้น เพราะอาการเดียวกันมักมีหลายคนเจอ คนอื่นจะได้เห็นวิธีแก้ขัดไปด้วยโดยไม่ต้องถามซ้ำ

**เพดานนับรายกลุ่ม** ไม่ใช่รายคน ไม่งั้น 5 คนในกลุ่มเดียวกันจะแจ้งได้ 15 เรื่องต่อวัน

### ข้อจำกัดที่ต้องรู้

**Apps Script อ่าน header ของ request ไม่ได้** จึงตรวจ `X-Line-Signature` ตามที่ LINE
แนะนำไม่ได้ ต้องใช้กุญแจใน URL แทน ซึ่งอ่อนกว่า — ใครรู้ URL ก็ยิงปลอมได้

ชดเชยด้วย **`ALLOW`** (รับเฉพาะ userId ที่อนุญาต) และ **เพดาน 3 เรื่อง/คน/วัน**
เพราะ 1 เรื่อง = หัวหน้าทีมทำงาน 1 รอบ = เงินจริงราว $0.6

**ไม่รับวิดีโอกับไฟล์แนบ** ใหญ่ ช้า และแทบไม่เคยช่วยให้เข้าใจอาการมากกว่ารูปนิ่ง

**ไม่เก็บ LINE userId ลงใน issue** เก็บไว้ใน Script Properties ของ Apps Script แทน

### รูปที่แนบมาไปอยู่ไหน

รูปไม่ได้แนบลง issue เพราะ `store` กับ `plan` เป็น public แต่อัปเข้า
**`nse-manufac/intake`** ซึ่งเป็น private แล้ว issue เก็บไว้แค่บรรทัดเดียวว่า

```
📎 มีหลักฐานแนบ 2 รูป เก็บไว้ใน repo ส่วนตัว · `evidence: store-20260811-a1b2c3d4`
```

**ไม่มีลิงก์ ไม่มีเนื้อหา** คนที่ไม่มีสิทธิ์อ่าน `intake` เห็นได้แค่ว่ามีรูปกี่รูป
`agent-triage.yml` ของแต่ละ repo อ่านรหัสนั้นไปดึงไฟล์ลงมาที่ `evidence/` ก่อนปลุก agent

**ลำดับสำคัญมาก — bot อัปรูปให้เสร็จก่อนเปิด issue เสมอ** เพราะการเปิด issue
คือสิ่งที่ปลุก workflow ถ้าอัปทีหลัง workflow อาจวิ่งไปถึงขั้นดึงหลักฐานตอนที่ไฟล์ยังขึ้นไม่ครบ
แล้วเห็นเป็น "ไม่มีรูปแนบมา" ซึ่งแยกไม่ออกจากกรณีที่ไม่มีรูปจริง ๆ
ด้วยเหตุนี้ชื่อโฟลเดอร์จึงเป็นรหัสสุ่ม ไม่ใช่เลข issue — ตอนอัปยังไม่มีเลขให้ใช้

กฎการรับรูป

- รับเฉพาะรูปที่ส่งตามหลัง `#แจ้ง` **ระหว่างที่ bot กำลังถามว่าโปรแกรมไหน** (10 นาที)
  รูปที่คนในกลุ่มส่งคุยกันตามปกติจะไม่ถูกดูดเข้าระบบ
- สูงสุด 4 รูปต่อเรื่อง
- อัปไม่สำเร็จก็ยังเปิดเรื่องให้ตามปกติ และบอกคนแจ้งตรง ๆ ว่ารูปเก็บไม่ได้

ยังต้องใส่ secret **`INTAKE_READ_PAT`** (Contents: Read บน `intake`) ใน `store` และ `plan`
ไม่ใส่ก็ยังทำงานได้ แค่ agent จะไม่เห็นรูป

### ตอบคำถามที่หัวหน้าทีมถามกลับมา

เมื่อหัวหน้าทีมข้อมูลไม่พอ มันจะถามกลับมาที่แชท พนักงานตอบด้วย

```
#ตอบ เห็นซ้ำที่ช่องเลือกรหัสตอนคีย์รับเข้า
```

คำตอบไปต่อเป็น**คอมเมนต์ในเรื่องเดิม** ไม่กลายเป็นเรื่องใหม่ แล้วปลุกหัวหน้าทีมให้อ่านต่อ

**ผูกกับ "คน" ไม่ใช่ "กลุ่ม"** เพราะในกลุ่มเดียวกันหลายคนมีเรื่องค้างพร้อมกันได้
ส่วนคำตอบยังส่งกลับเข้ากลุ่มเหมือนเดิม

**ทำไมมันไม่วนไม่จบ** — คอมเมนต์ของ bot มาจาก PAT จึงปลุก workflow ได้
ส่วนคอมเมนต์ที่หัวหน้าทีมเขียนตอบใช้ `GITHUB_TOKEN` ซึ่ง **GitHub ไม่สร้าง run ใหม่ให้**
สองอย่างประกอบกันแปลว่าวนไม่ได้โดยธรรมชาติ ไม่ต้องมีตัวนับกันลูป

**เพดานสองชั้นที่ต้องตรงกัน**

| ที่ | ค่า | นับอะไร |
|---|---|---|
| `MAX_REPLY` ใน `Code.gs` | 2 | จำนวนครั้งที่พนักงานตอบได้ต่อเรื่อง |
| `AGENT_MAX_TRIAGE_ROUNDS` (repo variable) | 3 | จำนวนคอมเมนต์ของหัวหน้าทีมต่อเรื่อง |

รอบแรกตอนเปิดเรื่องนับเป็น 1 อยู่แล้ว **2 + 1 = 3** ถ้าตั้งไม่ตรงกัน
พนักงานจะพิมพ์คำตอบที่ไม่มีใครอ่านโดยไม่รู้ตัว

> ⚠️ `issue_comment` ยิงเมื่อ **ใครก็ได้** คอมเมนต์ และ repo เป็น public
> `agent-triage.yml` จึงตรวจทั้งคนเปิด issue และ**คนคอมเมนต์**ว่าเป็นเจ้าของ
> พร้อมกันคอมเมนต์บน PR ออกไปด้วย เพราะ event เดียวกันยิงจากทั้งสองที่

**รอบที่มาจากคอมเมนต์จะไม่ส่งไม้ต่อให้ช่างซ่อมอัตโนมัติ** เพราะป้าย `ready-to-fix`
ค้างอยู่บน issue ได้แม้ PR จะ merge ไปแล้ว ถ้าปล่อยไว้ ทุกคำตอบจะสั่งงานซ้ำเรื่องที่จบแล้ว
และด่านกันงานซ้ำจับไม่ได้ เพราะมันดูจากสาขาที่ถูกลบไปตอน merge

### ทดสอบตรรกะ LINE โดยไม่ต้องยิงของจริง

```
node line/test_line.js
```

สวมของปลอมให้ Apps Script ทั้งหมด **ไม่ต่อเน็ต ไม่เรียกโมเดล ไม่เสียเงิน**
ครอบคลุมเคสที่พังแล้วเงียบ — รูปหาย รูปหลุดไปที่สาธารณะ bot พูดในกลุ่มโดยไม่มีใครเรียก
และคำตอบไปเข้าเรื่องของคนอื่น

## รันในเครื่อง

ต้องมี `gh` ที่ล็อกอินแล้ว กับ Python 3
